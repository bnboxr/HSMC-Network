Goal: Design and deploy a public, scalable, interoperable and ultra‑secure blockchain ecosystem resilient to classical attacks, AI‑assisted attacks, reverse engineering and quantum threats. The platform will provide privacy‑by‑choice features, native stablecoins, instant conversion, liquidity pools and an integrated payment processor able to interoperate with card networks via licensed partners.

Privacy by choice: per‑transaction Public / Private toggle.
Staking, mining, farming — configurable hybrid PoS + optional PoW.
Instant native conversion between the protocol token and other currencies (crypto & fiat).
Native stablecoins: USDHSMC, EURHSMC, XAUHSMC (gold‑pegged) with real‑time price feeds.

Cross‑chain interoperability: bridges, swaps, state proofs.
Wallet ecosystem: web, mobile, desktop, hardware; FIDO2 & MPC support.

Immutability & auditability: immutable ledger with proofs/commitments for private data.
Defense in depth: layered security (crypto, protocol, network, infra, UX, ops).
Hybrid & post‑quantum cryptography: classical + PQC primitives by default.
Privacy by choice & selective disclosure: view‑keys and threshold reveal for audit/regulatory requests.
Off‑chain primitives: state channels, rollups, L2 for scalability and privacy.

3. General architecture
3.1 Consensus & layering
Configurable hybrid consensus (BFT PoS / Tendermint‑like, DPoS/PoS with delegation) with optional PoW for mining. Layered architecture: secure mainnet and L2 solutions (rollups, state channels) to increase throughput and privacy. Sharding considered for long‑term scalability.

3.2 Crypto stack
Signatures: Ed25519 for compatibility, PQC by default (CRYSTALS‑Dilithium for signatures, CRYSTALS‑Kyber for KEM). Hybrid key exchange: X25519 + Kyber. Hashing: SHA‑3 / Keccak. Symmetric crypto: AES‑256. ZK privacy: zk‑STARKs as the primary mechanism (no trusted setup preferred), with SNARK compatibility where necessary.

3.3 Key modules
Privacy Engine (zk‑STARK prover + verifier)
Shielded pools: commitments, nullifiers, Merkle trees
Cross‑chain Interoperability Layer (bridges, relayers, state proofs)
Oracle Layer with multi‑source aggregation & validation
Liquidity Pool Manager (fee collection, reinvest automation, AMM + optional concentrated liquidity)
Node types: Validator nodes, Full nodes, Sentinel/security nodes, Sequencers for L2
4. Public / Private model (ON / OFF)
Private (OFF): Transactions can be on‑chain shielded (commitments + zk proofs) or off‑chain (state channels). Data remains encrypted/hidden; nullifiers prevent double spend. Users can selectively reveal transaction details for audits.

Public (ON): Transparent transactions validated on‑chain.

Selective disclosure: view‑keys and threshold reveal (e.g. 3 of 5) for compliance/audit requests.

Initial supply proposal: 500,000,000 HSMC (adjustable).

Utility: gas, staking rewards, governance votes, premium feature access.
Fee policy: base fee 1 EUR/USD; can rise to 3 EUR/USD under heavy congestion. Special mechanism: if user balance is very small (below threshold), a minimal fee of 0.10 applies to avoid draining their balance.
Fees are reinvested into liquidity pools to bootstrap liquidity and stability.

# 0. Document Purpose

This document defines the technical, economic, security, privacy, payment and interoperability architecture of the HSMC ecosystem.

HSMC is designed as an independent blockchain network developed from its own protocol and implementation, rather than being a token or application deployed on Bitcoin, Ethereum or another external blockchain.

The ecosystem consists of:

* **HSMC Network** — the blockchain protocol and decentralized network.
* **HSMC** — the native protocol asset.
* **HSMC Node** — the software implementing network participation, consensus, state validation and synchronization.
* **HSMCPay** — the native payment and settlement infrastructure.
* **HSMC Wallet** — user-facing wallet infrastructure.
* **HSMC Privacy Layer** — privacy-preserving transaction infrastructure.
* **HSMC Liquidity Layer** — native liquidity pools, conversion and settlement mechanisms.
* **HSMC Interoperability Layer** — bridges, external payment rails and other networks.
* **HSMC Stable Assets** — protocol-native stable-value assets subject to appropriate reserve, oracle and legal models.

### Important terminology clarification

Original concept:

(**"HSMC is both the blockchain and the native token, sharing identical architecture, functionality and economic rules: same security-first technology, same modules, same UX."**)

Revised definition:

**HSMC Network** refers to the blockchain protocol and decentralized network.

**HSMC** refers to the native asset of that network.

They are therefore part of the same native ecosystem, but they are not technically the same object.

This distinction exists so developers, auditors, regulators and users can clearly distinguish:

**protocol → network → node → asset → payment layer → wallet.**

---

# 1. Executive Summary

HSMC aims to design and deploy a public, scalable, interoperable and security-first blockchain ecosystem capable of operating under hostile network conditions and resisting a broad range of classical, automated, AI-assisted and future cryptographic threats.

The system is designed around:

* decentralized operation;
* verifiable settlement;
* privacy by choice;
* post-quantum cryptographic readiness;
* fault tolerance;
* native payment infrastructure;
* native liquidity;
* stable-value assets;
* cross-chain interoperability;
* developer accessibility;
* hardware-backed security;
* selective disclosure;
* transparent protocol rules.

The fundamental objective is not merely to create another cryptocurrency.

The objective is to create an **independent digital value-transfer and settlement infrastructure**.

HSMC should allow users to transfer value directly within the HSMC ecosystem without requiring Visa, Mastercard, PayPal, Stripe, an exchange or another blockchain to process native HSMC-to-HSMC transactions.

External systems may be connected for interoperability, fiat conversion, card payments, banking access, liquidity and other services, but such external systems should not constitute a single point of failure for native HSMC transactions.

### Core principle

> **External systems should connect to HSMC. HSMC should not require external systems to function internally.**

---

# 2. Vision

HSMC is intended to provide a payment and settlement environment where:

* transactions are verifiable;
* privacy is controlled by the user;
* network operation is decentralized;
* infrastructure failures are isolated;
* value can move globally through multiple rails;
* external payment networks can be integrated without becoming mandatory;
* users can prove that a transaction occurred without exposing unnecessary transaction details;
* the system can evolve toward post-quantum security;
* developers can build directly on HSMC.

The long-term objective is a network where the question is not:

> "Which company processes my payment?"

but:

> "Which protocol validates and settles my transaction?"

---

# 3. Design Principles

## 3.1 Decentralization

No single company, server, payment provider, exchange, bank, validator, liquidity provider or external network should be required for native HSMC-to-HSMC operation.

The system must minimize single points of failure.

---

## 3.2 Immutability and Auditability

The ledger must provide cryptographically verifiable transaction history and state transitions.

Private transactions must still generate verifiable cryptographic evidence that the protocol rules were satisfied.

---

## 3.3 Defense in Depth

Security is implemented across multiple layers:

1. cryptography;
2. consensus;
3. transaction validation;
4. networking;
5. node security;
6. wallet security;
7. infrastructure;
8. application security;
9. operational security;
10. monitoring;
11. incident response;
12. user security.

No single security mechanism should be treated as sufficient by itself.

---

## 3.4 Privacy by Choice

(**Original: "per-transaction Public / Private toggle."**)

Each supported transaction may allow the user to choose between:

### Public mode

Transaction information intended by the protocol to be public is recorded transparently.

### Private mode

Transaction details are protected through cryptographic privacy mechanisms while the network continues to verify transaction validity.

Privacy must not mean that the transaction does not exist.

Instead:

> **The existence and validity of a transaction can be proven without automatically exposing its private contents.**

---

## 3.5 Selective Disclosure

Users may selectively prove information about a private transaction.

Possible mechanisms include:

* view keys;
* transaction proofs;
* cryptographic commitments;
* threshold-controlled disclosure;
* audit-specific disclosure mechanisms.

Example:

A user may prove:

> "This transaction belongs to me."

without publishing the complete transaction history to everyone.

---

# 4. HSMC Network Architecture

## 4.1 Protocol

HSMC is an independent blockchain protocol.

The implementation is not required to inherit Bitcoin, Ethereum or another blockchain's consensus or ledger structure.

The current implementation is developed using Rust for core blockchain and node components, with additional ecosystem components implemented in appropriate languages according to security, performance and platform requirements.

---

# 5. Consensus Architecture

(**Original: "Configurable hybrid consensus (BFT PoS / Tendermint-like, DPoS/PoS with delegation) with optional PoW for mining."**)

The HSMC consensus layer is intended to support a configurable security architecture combining Byzantine Fault Tolerant proof-of-stake mechanisms with optional mining mechanisms where justified by the final protocol design.

The exact consensus mechanism must be finalized through:

* formal specification;
* simulation;
* adversarial testing;
* economic analysis;
* performance benchmarking;
* security review;
* formal verification where practical.

Possible components include:

* PoS;
* delegated participation;
* BFT-style finality;
* optional PoW;
* validator rotation;
* slashing or equivalent economic penalties;
* anti-Sybil mechanisms.

The final implementation must avoid combining mechanisms merely for marketing purposes. Every consensus component must have a clearly defined security or economic function.

---

# 6. Node Architecture

HSMC supports multiple node roles.

## 6.1 Validator Node

Responsible for:

* validating transactions;
* participating in consensus;
* validating blocks;
* maintaining state;
* participating in finality.

---

## 6.2 Full Node

Maintains the blockchain state and validates network data without necessarily participating directly in consensus.

---

## 6.3 Sentinel / Security Node

Designed for:

* anomaly detection;
* network monitoring;
* threat detection;
* peer observation;
* security telemetry;
* attack detection.

Sentinel nodes must not automatically become trusted authorities.

---

## 6.4 L2 Sequencer

Where L2 infrastructure is deployed, sequencers may order L2 transactions according to defined protocol rules.

The system must define appropriate escape, verification and fraud/proof mechanisms so that L2 infrastructure does not become an uncontrolled centralized dependency.

---

# 7. Cryptographic Architecture

(**Original: "Signatures: Ed25519 for compatibility, PQC by default (CRYSTALS-Dilithium for signatures, CRYSTALS-Kyber for KEM)."**)

HSMC will use a hybrid cryptographic strategy combining mature classical primitives with standardized post-quantum primitives where appropriate.

The current architecture should be updated to use the current NIST-standardized terminology:

* **ML-DSA** — derived from CRYSTALS-Dilithium, for post-quantum signatures.
* **ML-KEM** — derived from CRYSTALS-Kyber, for post-quantum key encapsulation.
* **X25519** — classical elliptic-curve key exchange where appropriate.
* **Ed25519** — classical signatures where compatibility or specific protocol requirements justify their use.

(**Original: "CRYSTALS-Dilithium" and "CRYSTALS-Kyber"**)

The project should maintain algorithm agility so that cryptographic primitives can be replaced if future research identifies weaknesses or superior standardized primitives.

---

# 8. Hashing and Symmetric Cryptography

Candidate primitives:

* SHA-3;
* Keccak where protocol compatibility requires it;
* AES-256;
* authenticated encryption modes appropriate to the protocol;
* secure random generation;
* hardware-backed randomness where available.

Cryptographic choices must be finalized through security review rather than selected solely for performance.

---

# 9. Post-Quantum Security

HSMC is designed to be **post-quantum ready / quantum-resistant where supported by its selected cryptographic primitives**.

(**Original: "ultra-secure ... quantum threats"**)

No cryptographic system should claim absolute protection against unknown future attacks.

The objective is therefore:

> Minimize known quantum-vulnerability surfaces and provide cryptographic agility for future upgrades.

Sensitive operations may additionally support:

* hybrid classical + PQ signatures;
* hybrid key exchange;
* key rotation;
* forward secrecy;
* hardware-backed keys;
* threshold authorization.

---

# 10. Privacy Engine

The HSMC Privacy Engine is designed around cryptographic proofs rather than trust in a centralized database.

Candidate components include:

* zk-STARKs;
* Merkle trees;
* commitments;
* nullifiers;
* shielded state;
* encrypted transaction metadata;
* selective disclosure.

(**Original: "zk-STARKs as the primary mechanism (no trusted setup preferred), with SNARK compatibility where necessary."**)

zk-STARKs remain the preferred architecture where their performance and implementation requirements are appropriate.

SNARK-compatible mechanisms may be supported where there is a demonstrable engineering advantage.

---

# 11. Public Transactions

Public transactions are transparent according to the protocol's defined data model.

A public transaction may expose:

* sender/address;
* recipient/address;
* amount;
* fee;
* timestamp/block;
* transaction ID;
* transaction status.

The exact fields must be finalized by the protocol specification.

---

# 12. Private Transactions

Private transactions protect selected transaction information.

The blockchain may contain:

* commitments;
* nullifiers;
* encrypted data;
* proofs;
* transaction identifiers;
* state transition evidence.

The blockchain should not automatically expose:

* exact amount;
* real-world identity;
* private metadata;
* private recipient information.

The system must nevertheless allow the network to verify that:

* the sender had sufficient authority/funds;
* the transaction follows protocol rules;
* the same private output has not already been spent;
* the cryptographic proof is valid;
* the state transition is valid.

---

# 13. Transaction State Model

HSMC Pay should distinguish between transaction submission, blockchain confirmation and recipient receipt.

Proposed state model:

```text
CREATED
   ↓
SIGNED
   ↓
BROADCAST
   ↓
VALIDATING
   ↓
CONFIRMED
   ↓
FINALIZED
   ↓
SETTLED
   ↓
RECEIVED
```

Failure states:

```text
REJECTED
EXPIRED
FAILED
CANCELLED
INVALID
```

The final protocol must define which states are consensus-level and which are application-level.

# 14. Recipient Confirmation

A key HSMCPay requirement is the ability to distinguish:

> "The sender submitted the transaction."

from:

> "The network finalized the transaction."

and:

> "The recipient wallet recognized and received the funds."

A payment receipt may therefore contain:

* transaction ID;
* finality proof;
* recipient confirmation;
* timestamp/block reference;
* cryptographic proof where appropriate.

This allows a user to prove that a payment completed without requiring the public disclosure of unnecessary private information.

# 10. Block Height

Genesis block:

```text
height = 0
```

Each subsequent block increments height by exactly one.

A block claiming:

```text

```

where `N != 1` MUST be rejected unless the protocol explicitly defines checkpoint synchronization.

```text

   ↓ previous_hash

   ↓ previous_hash
Block N-2
```

# 18. Canonical Serialization

The same transaction MUST produce exactly the same byte representation on every implementation.

Requirements:

* deterministic integer encoding;
* deterministic length encoding;
* no ambiguous representations;
* no platform-dependent serialization.

Possible implementations:

* custom binary codec;
* canonical CBOR;
* another formally specified binary format.

JSON MUST NOT be used as the consensus serialization format.

JSON may be used at RPC/API boundaries.

A transaction with an invalid nonce MUST be rejected according to the protocol's nonce rules.

# 22. Private Transaction

# 23. Privacy Invariants

2. the consumed state exists;
3. the consumed state has not already been spent;
4. the transaction does not create unauthorized value;
5. the proof is valid;
6. the resulting state is valid.

# 32. Small-Balance Protection

(**Original: "minimal fee of 0.10 applies to avoid draining their balance."**)

The protocol may provide a minimum-fee protection mechanism.

However, a rule that allows a transaction to pay less than the actual network cost can create spam or economic attacks.

* protocol fee;
* subsidized fee;
* sponsored transaction;
* wallet UI protection.

Small balance
      ↓

# 66. Crash Recovery

If a node crashes during block processing:

1. restart;
2. inspect last durable state;
3. verify last finalized block;
4. recover incomplete operations;
5. synchronize missing data;
6. resume normal operation.

The database layer must provide atomicity sufficient for deterministic recovery.

# 67. Snapshot Synchronization

For large chains, nodes may use verified snapshots.

Snapshots MUST contain:

* state;
* block reference;
* state root;
* protocol version;
* verification metadata.

A node MUST cryptographically verify the snapshot before trusting it.

---

# 68. Fast Synchronization

Future optimization may support:

* checkpoint sync;
* state sync;
* snapshot sync;
* parallel block download.

Fast sync MUST NOT bypass cryptographic verification.

# 69. Time

Consensus-critical timestamps MUST NOT blindly trust local system time.

The protocol must define:

* allowed clock drift;
* block timestamp rules;
* validator time behavior;
* timestamp validation.

# 70. Randomness

If validator selection or protocol logic requires randomness, the randomness source must be explicitly specified.

Possible mechanisms:

* VRF;
* threshold randomness;
* commit-reveal;
* consensus-derived randomness.

Randomness MUST be resistant to trivial proposer manipulation.

* minimum fees;
* transaction size limits;
* mempool limits;
* peer rate limits;
* per-account transaction limits where appropriate;
* computational cost limits.

Anti-spam measures MUST NOT accidentally prevent legitimate low-value payments.
